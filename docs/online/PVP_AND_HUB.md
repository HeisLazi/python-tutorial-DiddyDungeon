# Private online hub and PvP: implementation contract

## Product scope

A private group of up to four players enters **Shax Champions House**, a compact shared, walkable space with the Colosseum, raid route, Sir Getrich, and group Leaderboards. The Colosseum offers friendly borrowed gear, normalized fair duels, and earned-gear duels for the private ladder. Players can still use the application offline.

## Safety and trust boundaries

- The desktop app holds its own save. A match must not mutate `progress.json`; the reward boundary is separately versioned and idempotent.
- Account identity is authenticated by the service. A room invitation authorizes joining only; it is not an account, a ranking identity, or a durable bearer login.
- Only the match service decides deadlines, task selection, accepted submissions, evaluation, hit points, match outcomes and ratings. No result, stance effect, rating, ownership claim, or timestamp sent by a client is trusted.
- Python from another player must never run in a desktop process or the existing local `/run` or `/check` endpoint. The evaluator needs an independently deployed, constrained worker with no network, bounded CPU, memory, processes, output and wall time; an ephemeral filesystem, strict limits and per-submission teardown are required. Docker alone is not assumed to be a complete security boundary for hostile multitenant execution.
- Each player sees their own code only. Evaluation returns bounded, safe feedback; it does not send source or hidden checks to the other player. A timed-out answer is resolved by the service.
- The existing two-tab demo and connection lobby are prototypes, not authenticated or safe to expose as online play. The demo's client-provided verdict is explicitly untrusted and cannot update a ladder.

## Minimum architecture

1. Authenticated private group membership and revocable invitations, with a group of at most four.
2. Shared-hub presence (ephemeral, bounded position updates) and profile appearance. Movement is visual; the service owns membership and the action permissions.
3. Match service with an explicit state machine: lobby → coding → evaluating → exchange → next round → finished, including idempotency, server deadlines, limited reconnect windows and explicit aborts. Each round has one submission per player.
4. An isolated Python evaluator, kept separate from the match coordinator, with an authenticated internal-only API. For offline development, the service must fail closed when no evaluator is configured.
5. Ranked settlement as a single idempotent transaction, constrained to group members and a curated, server-defined equipment pool. Friendly borrowed gear never modifies an inventory.
6. Windows and Linux desktop clients use the same hosted HTTPS/WSS protocol. A Linux build alone cannot establish that the Windows package works; verify each platform with its own installed client. macOS is out of scope for this release.

## Starting delivery milestones

1. Replace the local-only room demonstration with a protocol boundary that never accepts client-supplied correctness or runs submitted code in the coordinator.
2. Add authenticated group membership and a shared, compact walkable hub with four-player presence. Reuse the existing app's account session; avoid creating a separate password system.
3. Integrate a real, isolated execution worker, then implement a single coding chain through the match service. Handle both-answered, timeout, retry, reconnect, and double-submit cases.
4. Add equipment modes, animation events, and transactional ladder settlement only after the basic flow is stable.
5. Provision the actual HTTPS service, build desktop packages and verify using real Windows and Linux devices. Do not claim this is complete based on a same-machine preview.

## Current implementation status

> This section is a historical implementation log from the initial PvP slice. Its dated statements about deployment, ranked play, and platform builds are superseded by `ONLINE_SECTION_COMPLETION_PLAN.md` and `PRIVATE_RELEASE_PLAN.md`. Current live checks on 2026-11-09 confirm PapaSmurff serves the online API over Tailscale Funnel HTTPS, so players do not need a Tailscale client; Tailscale remains the host administration path. The release targets Windows and Linux, not macOS.

- PapaSmurff was prepared as a candidate Linux evaluator host. gVisor `runsc` is registered with the separate system Docker daemon; the existing rootless daemon and its running containers were left running. A copy of the evaluator worker was exercised there with correct and incorrect submissions, practice output, inaccessible host files, disabled network and a CPU-limited loop. Its loopback HTTP API accepted an authenticated correct answer and rejected an invalid credential and mismatched catalogue revision; that temporary API process was stopped after the check. This is an initial host check, not a complete hostile-code security review or a deployed match service.
- The Supabase project was restarted after a database outage. The private group, ladder and verified gear migrations were applied; table RLS, Realtime policies, and denial of client-side gear awards and ladder settlement were checked. Public Realtime channels were disabled. A rolled-back test verified that a non-member cannot read a group and can join with an invitation. End-to-end authenticated presence checks remain outstanding.
- The match service can connect to a colocated evaluator through an absolute `unix:///...` socket URL as well as HTTPS. The socket must be placed in a private directory with access limited to the two service identities; the worker credential remains required. The real client, worker and gVisor runner were checked together over a temporary private socket on PapaSmurff. No evaluator was left listening after the check.

- A disposable Linux-only local duel playtest runs with `python -m ide.server.online.playtest` and the Vite development entry `duel-dev.html?player=1` / `?player=2`. It uses the real duel component and coordinator, fixed test identities, in-memory state and a bubblewrap runner. It binds to loopback and is intended only for trusted local players; it is not a hosted, authenticated or production sandbox. No campaign save is used. Two agents completed a three-round match in separate browser tabs, including practice, correct and incorrect submissions, bonus healing and the final result. This does not establish cross-device or installed desktop functionality.

- `ide/server/online/duel.py` owns coding deadlines, stances and round resolution. `coordinator.py` handles recipient-specific invitations, hidden challenge selection, evaluation dispatch and cancellation. It can persist state in a dedicated single-instance SQLite store; ranked settlement remains disabled.
- `service.py` is a separate FastAPI app. It authenticates each request against Supabase Auth and checks group membership with the requesting user's RLS-scoped token. It reads no local game save and accepts no correctness verdict from a client. It fails closed if no evaluator is configured.
- `worker/service.py` is a separate evaluator API. `sandbox.py` requires a preconfigured Docker `runsc` runtime and a pinned local image ID; no standard-container or host-Python fallback exists. Containers are nonroot, read-only, without networking or host mounts, with CPU, memory, process, file and wall-time limits. The worker compares returned typed values with its own private expected results; it never returns the hidden checks or program output to a rival.
- The worker has been exercised with gVisor on PapaSmurff, including isolation and end-to-end execution checks. An evaluator outage cancels the duel without awarding a result. This is a private tailnet deployment, not a public service.
- `OnlineHideout.jsx` and `OnlineDuel.jsx` provide the in-app group/hideout and fair-duel flow. The default HTTPS service is PapaSmurff on the private tailnet; `VITE_QUESTLAB_ONLINE_URL` can override it at build time. The locally generated prototype on port 8901 is not that service.
- On 2026-11-07, two disposable authenticated accounts completed a three-round duel from Wazi and PapaSmurff using the actual hosted service and gVisor worker. The Wazi player used the app UI; the other device used an automated player. Private hideout presence, invitation, loadouts, practice, submissions and the final result were exercised. The disposable accounts were removed afterward.
- The Linux desktop launcher has been installed and its served interface has loaded cloud configuration using a disposable save. A full match between two installed desktop apps is still unverified. PapaSmurff's supervisor is transient and must be restarted after a host reboot; it deliberately keeps the public account key in memory. Ranked gear awards, consumables and a fully interactive terminal are outstanding. Windows and macOS desktop packages have not been built or checked.
- The ladder migration adds group-scoped read policies and an idempotent, service-role-only settlement function. A disposable database check covered a first win, retry, conflicting result and client execution privileges. The migration is applied, but ranked play remains disabled until match and equipment records are independently verified.
- Wazi lacks `runsc`; PapaSmurff's system Docker has the runtime and passed initial sandbox checks.
- Fair and friendly matches now have a server-owned loadout phase. Fair mode normalizes equipment effects; friendly mode borrows campaign weapon, armour and trinket definitions without changing inventory, applying explicitly displayed small PvP conversions. The match clock starts only after both players lock their loadouts. Unsupported weapon animations are disclosed. Consumables, ranked ownership and durable settlement remain unavailable.
- Both duel fighters can now display supported armour and weapon styles; the rival's staff and hand magic use a ranged casting reaction. `prototypes/duel-local/outfits-preview.html` is an isolated visual inspection aid, not an online match.
- The duel workspace now includes a bounded, isolated **practice run** with optional stdin and private output. It is a program runner, not an interactive shell; the worker requires the same gVisor deployment as answer checks. Practice does not submit an answer, score a round, or show output to the opponent.
- In-progress duel source and match references are saved only in tab-scoped session storage, keyed by account and group; credentials and opponent code are excluded. Reloading the tab can reconnect while the server match is retained. Browser recovery does not survive closing the tab; a configured durable server can restore safe match states after a restart.
- One timed bonus question between early rounds is server-resolved. Players privately choose an answer and a small healing, guard or attack reward; a miss or timeout does no damage. The correct explanation is revealed only after both answers resolve or the bonus timer expires.
- The coordinator can now use a dedicated SQLite database for recoverable single-instance matches and invitations. It stores neither source code nor account tokens, uses an exclusive host-process lock and fails closed on storage errors. If the process restarts with an evaluation in flight, the match is cancelled without a result; previously accepted, completed worker verdicts and pending invitations can be restored. This is not multi-instance storage and ranked settlement remains disabled.
- A locally verified migration adds a server-issued gear ledger. Only a trusted award service can write it; players can read only their own verified items, and repeated or conflicting award IDs are handled transactionally. Ranked selection has a bounded approved pool and rejects unverified items. Existing local campaign saves are not proof of verified ownership, and the campaign reward pipeline has not yet been connected. No existing gear has been imported or removed.
