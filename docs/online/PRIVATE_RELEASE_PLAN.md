This is a small personal learning game, not a commercial launch. PapaSmurff is the always-on host. ## Acceptance milestones

1. **Recovery and release boundary.** Inventory the current tree, save paths and build inputs; make verified backups of user state and a reviewable release source snapshot without bundling secrets or user progress. Document the supported Linux and Windows architectures. All work must leave the existing save usable.
2. **Reliable host and client-free access.** Make match service and isolated worker restart after failures and machine reboot without persisting API keys; validate startup, sandbox health, database recovery, updates, backup/restore and in-flight match cancellation. Use a practical HTTPS ingress such as Cloudflare Tunnel with existing sign-in and group checks, bounded code execution and no public worker, database or administration endpoints. Keep the setup appropriate for three players, and check that outside connections and the basic access boundaries work. Retain Tailscale for administration and fallback. Review provider/domain and tunnel credential requirements against the no-credentials-on-disk rule before deployment. Host shutdown or loss of Internet must produce a clear offline state, never false results.
3. **Self-contained clients.** Replace checkout-dependent and Unix-specific assumptions with packaged frontend, compatible Python backend/runtime and app-managed per-user data and workspace locations. Address Windows process/terminal handling. Install, update, uninstall and reinstall without deleting saves. Code execution in PvP remains on the isolated server. Verify the learning/editor features necessary for the product independently on each OS.
4. **Linux and Windows alpha.** Produce downloadable Linux and Windows installers with versioned checksums; install into clean environments with no repository or development tools. Use the available Windows VM only after assessing memory and storage. Complete two real app clients across devices: signup, private invite, presence, loadout, practice, duel, bonus, result, reconnect and failure recovery. Test an upgrade while preserving saves.
5. **Ranked and ladder.** Connect verified progression awards to the server-issued gear ledger without treating editable local saves as proof. Implement authoritative owned loadouts, idempotent results and group-scoped ladder updates, tie/disconnect rules, duplicate/retry handling, and an understandable ownership migration for existing saves. Keep ranked disabled until adversarial and real-client tests pass; friendly mode continues to offer the full borrowed gear catalogue.
6. **Release and operate.** Publish private, versioned installers by an agreed distribution channel, provide onboarding and host availability/status, back up the match database and recovery instructions, and verify a clean three-player rollout with two Windows clients and one Linux client without Tailscale on player devices. Keep accounts and invitations revocable; don't deploy public matchmaking. Track support and maintenance requirements and rollback.
7. **Later: raid and macOS.** Build project creation, task allocation/reassignment, shared progress, code review, completion verification, rewards and recovery. Treat macOS packaging, signing and real-device validation as a separate future milestone.

## Operating constraints

- Avoid using PapaSmurff's fanless GPU for builds or VM acceleration. Use CPU builds and software rendering if practical; confirm device assignment before launching a VM.
- Wazi and PapaSmurff both showed swap use and limited free RAM on initial inspection. Limit parallel jobs, measure headroom immediately before each heavy operation, avoid concurrent VMs/builds, and do not restart unrelated services or containers.
- Wazi's registered `Win11-Test` VM is configured for 4 GiB RAM and VGA graphics, with no GPU passthrough. It booted and completed Windows updates on 2026-11-07, and Lazi signed in. Its libvirt configuration has no guest agent. An isolated temporary uv/Python installation enabled real Windows backend checks; the VM does not have Rust, Node, Git or Tauri installed. Available host RAM fell below 2 GiB and swap use rose during the test, so do not run a concurrent build without reassessing headroom.
- Agents may inspect and implement in the authorized worktree; keep writers coordinated and never expose credentials in logs or agent prompts. External-model CLI usage must respect the user's active accounts, repository privacy and resource limits.
- Tailscale remains an optional testing and administration route; the release target requires no Tailscale client on friends' devices. Friends still need to accept their own game invitations and participate in final real-device playtests.
- Publisher identity verification, external account approvals, any required domain purchase and access to friend-owned devices are outside the agent's control. Build and verification work can start without them.
