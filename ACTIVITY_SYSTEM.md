# Python Quest Lab — Dev Activity League

The learning RPG and the dev-activity competition are related, but they are **not the same score**.

Learning progression comes from PYR-verified evidence: concepts, interviews, mobs, bosses, creativity, shields and explanations.

Dev Activity comes from **Git commit history** and is machine-derived into `activity.json`.

This separation matters: a player cannot gain Mastery Shields by spamming commits, and an AI tutor cannot invent commit activity.

## What is tracked

The activity sync currently records:

- commits in the last 7 days;
- commits in the last 30 days;
- active development days in the last 7 and 30 days;
- current commit streak;
- longest commit streak visible in the scan window;
- active branches in the last 30 days;
- a 30-day daily activity history;
- a branch activity breakdown;
- **Activity Score** for friendly competition.

`activity.json` is generated automatically and should not be manually edited to increase stats.

## Activity Score

The default score is intentionally biased toward **showing up consistently**, not creating dozens of tiny commits in one evening.

For the rolling 30-day window:

```text
Activity Score =
    active days × 12
  + effective commits × 2
  + current streak × 8
  + active branches × 5
```

`effective commits` are capped at **5 commits per active day** for scoring.

The raw commit count is still displayed publicly, but commits above that daily cap do not keep increasing the competitive score.

The branch bonus is also capped. This prevents creating pointless branches just to farm score.

The exact numbers are stored in `activity_config.json` so forks use the same rules unless the ruleset is intentionally changed.

## Two streaks, two meanings

Python Quest Lab has two separate streaks:

### Learning streak

Stored in `progress.json` and verified by PYR. A day counts when meaningful learning happened: implementation, debugging with understanding, interviews, mobs, etc.

### Dev streak

Stored in `activity.json` and derived from Git history. A day counts when a qualifying commit exists.

These should stay separate. The learning streak says **I learned**. The dev streak says **I shipped code**.

## Anti-spam rules

Activity competition should encourage building, not bad Git habits.

- raw commits are visible, but scoring caps effective commits per day;
- commits generated by the activity bot are ignored;
- repeated empty/no-op commits should not be encouraged;
- branch activity is capped for scoring;
- commit count does not grant XP, coins, shields or boss clears;
- AI tutors must never manually award Activity Score.

If someone wants to make 12 real commits in a day because they built 12 meaningful checkpoints, that is fine. The public raw count will show 12. The competitive score simply stops rewarding volume after the cap.

## Rival Mode

A rival entry can expose both:

- `progress.json` — verified learning/RPG state;
- `activity.json` — machine-derived Git activity.

Recommended rival fields:

```json
{
  "name": "FriendName",
  "progress_url": "https://raw.githubusercontent.com/OWNER/REPO/main/progress.json",
  "activity_url": "https://raw.githubusercontent.com/OWNER/REPO/main/activity.json"
}
```

If `activity_url` is omitted, the dashboard may infer it by replacing `progress.json` with `activity.json` in the same public raw URL.

## Competition modes

The dashboard can show three useful comparisons:

- **Learning Power** — XP, shields, bosses, interviews, clean clears;
- **Dev Activity** — commit-derived activity score;
- **Rival Score** — both displayed together rather than pretending they measure the same thing.

Do not silently merge the two into one XP economy. Someone can be the more active developer this month while the other player has stronger demonstrated Python mastery.

That tension is part of the fun.

## Automation

`.github/workflows/sync-activity.yml` runs after pushes, on a daily schedule and manually.

It runs `tools/sync_activity.py`, which:

1. reads public/authorized commit history across branches;
2. deduplicates commits by SHA;
3. ignores activity-bot commits;
4. calculates the rolling metrics;
5. writes `activity.json`;
6. refreshes the public README activity block;
7. commits those machine-derived files back to `main`.

The sync commit itself starts with `chore(activity):` and is excluded from future activity calculations.

## Fork setup

When a friend forks the campaign:

1. change `activity_config.json -> player_login` to their GitHub username;
2. optionally change `utc_offset_hours`;
3. keep the scoring constants the same for fair competition;
4. make sure GitHub Actions has `contents: write` permission for the repo;
5. run **Sync Dev Activity** manually once.

After that, activity should maintain itself as they work.
